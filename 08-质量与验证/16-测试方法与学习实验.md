# 第16章 测试方法与学习实验

> [!abstract] 本章在全流程中的位置
> 最后一章把算法变成可验证工程：怎样从真实入口运行场景，怎样区分稳定、精度、状态职责和显示，怎样设计outage与高动态测试，以及哪些结论可以写、哪些不能写。

## 16.1 四层验证金字塔

| 层 | 输入 | 证明什么 | 不能替代什么 |
|---|---|---|---|
| 公式/单元 | 确定性向量 | 符号、单位、边界、时标 | 真实量化噪声 |
| 模块集成 | 合成PDI | 命令确认、状态、清窗 | 真实相关协方差 |
| 真实IQ闭环 | StarGen→StarTrack | 完整相关器和闭环 | 捕获概率 |
| 来源移交 | StarAcq→adapter→StarTrack | 同版本真实移交 | 全矩阵资格 |

纯Observer单测通过不能证明生产路由调用了它；一个60 s桥接smoke也不能证明108例捕获移交矩阵。

## 16.2 runner、analyzer和算法各自做什么

| 角色 | 职责 | 明确禁止 |
|---|---|---|
| StarGen | 生成冻结物理场景 | 读取跟踪结果调信号 |
| StarTrack | 跟踪闭环 | 读取场景真值控制 |
| runner | 展开case、生成命令、冻结SHA、恢复运行 | 实现算法补偿 |
| analyzer | 以真值评分日志 | 改写跟踪命令或结果 |

runner看起来“复杂”，是因为它负责可复现证据链，不应该承担物理跟踪算法。

## 16.3 四种通过结论必须分开

### 稳定跟踪通过

- 管道正常结束；
- 同步和频率有效率达到门；
- 无锁后失步、重捕、PDI/cmd错误；
- 目标状态段持续驻留；
- 误差没有发散。

### 物理精度通过

- Doppler RMS不超过5 Hz；
- Doppler P95不超过10 Hz；
- 码误差P95不超过0.2 chip；
- 观察符号和动态响应符合算法预期。

### 状态职责通过

- 专门探针中，入口、candidate、pending、commit符合职责；
- 动态超限才进入Dynamic链；
- aid只有明确输入才进入；
- 状态变化等待命令确认。

### 显示测量通过

- C/N0参考窗口与输出窗口一致；
- bias和P95过门；
- valid rate与非物理解数量过门；
- 显示失败不应自动否定闭环跟踪。

最终报告可以是 `tracking_pass=true, display_pass=false`，但不能把它写成overall qualification pass。

## 16.4 频率观察有效率与使用率

定义：

$$
R_{valid}=\frac{N(\text{freq valid})}{N(\text{评分历元})},
$$

$$
R_{used}=\frac{N(\text{freq used})}{N(\text{评分历元})}.
$$

观察器长窗口可能只在每160/320 ms成熟，而日志20 ms一行。如果“未成熟行”也放进分母，使用率会天然很低。因此正式指标必须明确统计口径：是所有日志行、所有ready机会，还是目标状态下的可用更新机会。

芯片源码通常更关心观察门、连续确认和状态计数，不会把一个runner计算的全行比率直接当环路公式。使用率是测试诊断量，不应反向塞进生产控制。

## 16.5 所有场景都应从真实入口演化

测试HighDynamic不应冷启动强制状态=HighDynamic。正确过程：

1. 从ShortFast或明确辅助入口开始；
2. 让捕获后牵引、同步和普通状态建立；
3. 场景动态逐渐变化；
4. 观察FSM是否根据残余证据升级；
5. 动态下降后观察恢复链。

这样才能同时验证入口、状态切换和目标职责。强制内部状态只适合短单元测试，不属于真实闭环资格。

## 16.6 非零handoff时间轴

若起始样点为$S$、采样率$f_s$：

$$
T_0=\frac{S}{f_s}.
$$

StarGen从绝对时间0生成信号，TrackRunner丢弃前$S$个样点而不提前推进闭环。评分窗口$[45,60)$ s相对移交，对应绝对场景时间：

$$
[T_0+45,T_0+60).
$$

Doppler、码相位、TCXO和C/N0真值必须在绝对时间求值；结果中的first sync和状态timeline再减$T_0$变成相对移交时间。

## 16.7 Q16码相位合同

runner先把请求误差量化到Q8或Q16，再按码长回绕：

$$
q_{16}=\operatorname{round}(e_{chip}\times65536).
$$

对B1C请求$+0.35$ chip，Q8实际为：

$$
\frac{90}{256}=0.3515625\ \text{chip}.
$$

报告必须同时保存requested、applied和原始整数，不能把量化后值伪写成精确0.350000。

## 16.8 outage测试怎样写对

![[../90-附件/图RT-11_outage时间轴.svg]]

正式日志和场景服务以20 ms为评分网格。outage平台应使用半开区间：

$$
[t_{start},t_{end}).
$$

要求：

- $t_{start}$和$t_{end}$严格落在20 ms网格；
- 边沿前最后一点仍是正常功率；
- 平台内每点都是outage目标功率；
- 恢复边沿第一点恢复正常；
- 非零pilot offset加入StarGen总时长；
- analyzer按相对handoff时间报告恢复延迟。

线性插值若把边沿样点算进平台，会制造20 ms off-by-one，24例都必须使用同一生成合同。

## 16.9 随机场景大回归怎样评分

每个case至少输出三组结论：

### A. 稳定性

- 最终是否仍锁；
- 锁后是否失步/重捕；
- PDI/cmd/overflow是否为0；
- 频率和码是否有限且不发散；
- 最长连续有效段。

### B. 精度与算法预期

- Doppler RMS/P95；
- code P95；
- 观察使用和新鲜度；
- slew是否降低真实误差；
- 动态升降是否在独立证据后发生。

### C. 状态职责

- 记录实际路径和驻留；
- 随机场景不强制最终状态名；
- 专门探针才给出required/forbidden状态。

这样能区分“算法稳定但状态标签不同”“状态职责正确但精度未过”和“真正失锁”。

## 16.10 B1C高动态完整性门

B1C不能只看`sync`。高动态case至少联合检查：

- `b1c_wide_qualified`；
- coarse事件方向是否使真实码误差减小；
- slew start/stop和stop确认；
- center和fine qualified；
- pilot confirm与lock顺序；
- 锁定后频率RMS/P95；
- 码P95；
- 是否出现sync=true但误差持续漂移。

若`sync=true`但RMS几十Hz、码误差数chip，应判“同步标志假稳定”，不能算稳定通过。

## 16.11 建议的学习实验

### 实验1：相关峰

无噪声扫码偏差$-1$到$+1$ chip，画P/E/L/VE/VL功率，观察BPSK与BOC差异。

### 实验2：频率符号

固定Prompt幅度，注入$\pm10$ Hz，手算Cross/Dot和输出Hz，确认NCO修正方向。

### 实验3：命令时序

在epoch 100生成新step，证明PDI 100仍用旧命令、101才确认新命令。

### 实验4：载波辅助DLL

比较开/关$R_{aid}$时，同一5000 Hz Doppler下DLL需要承担的码率残差。

### 实验5：BOC slew

构造$\pm0.35$ chip，记录coarse方向、160 ms slew积分chip和停止命令，验证$|error|$下降。

### 实验6：FineCheck

让粗center成立但细误差RMS超门，观察PilotSync保持关闭；再给连续稳定细误差，验证下一PDI才开放。

### 实验7：状态职责

从ShortFast起步，分别构造强→弱、弱→强、动态上升→下降和aid失效，检查candidate/pending/commit。

```bash
cmake -S . -B build-release -G Ninja -DCMAKE_BUILD_TYPE=Release
cmake --build build-release --parallel 1
ctest --test-dir build-release --output-on-failure -j 1
python3 scripts/validate_fixed_catalog.py

```

算法修改还需跑受影响信号的强、中、弱、目标灵敏度、三档动态、状态切换和耐久。长StarGen→StarTrack管道串行执行并设置场景超时。

## 16.13 结论边界怎样写

### 可以写

- “冻结版本下，某信号三种子静态300 s tracking门通过”；
- “某个代表来源移交smoke通过”；
- “显示门独立失败，不影响本次闭环tracking scope”；
- “±0.6 chip为非资格pressure case”。

### 不可以写

- 一条seed通过就写完整资格；
- 手工handoff写成StarAcq端到端捕获通过；
- 静态通过写成1 Hz/s+TCXO通过；
- pilot-only写成data+pilot联合；
- observer纯噪声单测写成误锁概率证明；
- 不同commit/binary的结果拼成同版本总资格。

## 16.14 已明确废弃的方案

| 方案 | 禁止重新采用的原因 |
|---|---|
| 把场景动态标签直接映射状态 | 状态由残余物理证据决定 |
| 用`sync==1`定义稳定 | 可出现同步标志假稳定 |
| coarse方向进入DLL PI | 一次相位需求会变成永久码率偏置 |
| 用下一个ready撤销slew | gap会让slew无限保持 |
| BOC式(13)取绝对值 | 破坏有符号旁峰消除 |
| B1C码center后切Prompt FLL | 二次码未锁定时Prompt会给粗差 |
| 用20 s证明B1C同步 | 18 s搜索+18 s确认物理上不可能 |
| 为失败seed降门或翻符号 | 会破坏对侧场景且不可泛化 |
| 放宽精度门掩盖发散 | 把算法错误改名为通过 |
| 显示offset/floor修C/N0 | 失去物理测量意义 |

## 16.15 全书总结

StarTrack是一条严格分层的闭环：1 ms硬件相关提供事实，观察器把事实变成物理误差，FLL/PLL/DLL形成连续控制，Monitor压缩历史，FSM选择策略，命令在下一PDI确认。八种信号共享主线，但同步、功率目录和BOC牵引各有物理合同。测试必须从真实入口演化，并把稳定、精度、状态职责和显示分开。

如果你只记住一个调试方法，请记住：

> 找第一处错误历元，沿PDI→观察→used→命令确认追因果；不要只看最终状态和最后一段均值。
