# 第15章 源码地图与调试方法

> [!abstract] 本章在全流程中的位置
> 读完算法后，本章教你怎样进入源码和日志，而不是从最大的`track_engine.cpp`盲目搜索。核心方法是：先确定物理层级，再找第一处错误历元，最后沿“PDI→观察→使用→命令确认”因果链追踪。

## 15.1 源码目录地图

| 目录 | 职责 |
|---|---|
| `include/model`、`src/model` | 公共数据结构、状态、结果语义 |
| `src/signal` | 八信号物理目录 |
| `src/code` | 主码和二次码生成 |
| `src/hardware` | 整数NCO、混频、本地码、1 ms相关 |
| `src/pdi` | PDI解码和软件结构 |
| `src/integrator` | bit/导频相干组织 |
| `src/sync` | 数据bit、导频二次码同步与擦除 |
| `src/carrier_observer` | Cross/Dot、DFT、FMS、主码FLL |
| `src/code_observer` | 普通DLL、ASPeCT、粗码观察 |
| `src/carrier_loop` | FLL/PLL控制 |
| `src/code_loop` | 二阶DLL与载波辅助残差 |
| `src/monitor` | 频率/相位/DLL/C/N0/物理显示 |
| `src/tracking` | TrackEngine编排和FSM |
| `src/logger` | CSV快照，不反馈控制 |
| `src/runtime` | CLI、管道和跟踪运行器 |
| `tools` | campaign、分析器和证据编排 |
| `tests` | 与生产目录对应的确定性测试 |

## 15.2 推荐阅读顺序

1. `include/model/track_data.h`：认识PDI、观察、环路、同步、状态结果；
2. `src/signal/track_signal_spec.cpp`：知道当前信号的物理参数；
3. `src/tracking/track_engine.cpp::processPdi()`：只看六阶段调用顺序；
4. 当前问题对应的Observer；
5. 对应Loop；
6. 对应Monitor和FSM；
7. 最后看Logger和runner评分。

这样读能防止把日志字段、状态策略和鉴别器公式混成一层。

## 15.3 三个频率量

| 量 | 含义 |
|---|---|
| `nco_hz` | 该观察参考时刻的本地载波中心 |
| `physical_hz` | 相对该中心的物理残差 |
| `absolute_hz` | 两者之和，对应信号绝对基带频率 |

$$
f_{absolute}=f_{nco}+f_{physical}.
$$

日志中的“频率误差”还可能定义为NCO减truth或truth减NCO。分析器必须明确符号，不能看到正负就猜环路方向。

## 15.4 三个码量

| 量 | 单位 | 含义 |
|---|---|---|
| `code_phase` | chip或Q16 | 主码周期内本地绝对相位 |
| `code_chips` | chip | 观察器给出的局部修正误差 |
| `code_rate` | chip/s | 名义+载波辅助+DLL+临时slew |

码相位是周期量，比较误差必须取最短回绕距离。B1C长度10230 chip，$10229.9$与$0.1$相差0.2 chip，不是10229.8 chip。

## 15.5 调试总原则：找第一个错误历元

不要先问“为什么最后RMS是77 Hz”。先找：

1. 第一次观察符号错误；
2. 第一次 `valid` 但不合理；
3. 第一次 `used` 消费了坏观察；
4. 第一次命令把NCO推离真值；
5. 第一次同步标志与物理误差矛盾。

然后只分析这一点之前的一个完整观察窗。后续几千行通常只是同一错误的放大结果。

## 15.6 情况A：`freq_valid`很低

按顺序检查：

1. `freq_ready`是否按理论时标出现；
2. PDI/segment是否连续；
3. 当前source tap是否正确；
4. presence、quality、peak ratio谁失败；
5. 是否在码slew或同步边界频繁reset；
6. residual是否超出鉴频无模糊范围；
7. NCO换字是否正确重定时。

`ready`正常而`valid`低，说明路由在运行，问题在统计门或信号可观测性；`ready`本身不出现，才优先查时间轴和reset。

## 15.7 情况B：`freq_valid=true`但`freq_used=false`

检查：

- 当前状态是否hold frequency；
- 观察是否只读诊断；
- 是否physical_valid=false；
- 同历元是否触发nonPrompt、slew、lock边界而撤销；
- 是否有更高优先级的同步校频；
- 观察是否太旧。

不要为了让使用率好看，强行把所有valid送进FLL。used是控制许可，不是观察器通过率。

## 15.8 情况C：码误差发散

依次确认：

1. 真值口径是 `local-truth` 还是相反；
2. 抽头硬件几何与观察器配置是否一致；
3. 首个`CodeObs`是coarse还是fine；
4. coarse是否错误进入DLL PI；
5. slew开始、结束和stop确认是否精确；
6. 载波辅助是否使用正确载频和doppler符号；
7. BOC是否位于式(14)单调域；
8. 监测器是否把错误局部量误判为center。

必须画三条时间线：真实码误差、DLL残差、累计slew chip。只看最后`code_rate`无法区分载波辅助、PI和slew。

## 15.9 情况D：状态不切或切错

检查四层：

1. evidence是否ready/valid/mature；
2. desired函数选了哪个candidate；
3. candidate持续时间与active驻留是否足够；
4. pending命令是否被硬件确认。

最后再看邻接表。若物理精度完全合格但随机场景终态不同，先判断测试是否把输入标签当成状态职责，不要先改FSM门限。

## 15.10 情况E：`sync=true`但物理误差很大

这是“同步标志假稳定”。检查：

- PilotSync是否在码center前被打开；
- center证据来自coarse零还是FineCheck成熟；
- 锁定后是否错误回退粗包络；
- 码误差是否使用正确周期回绕；
- 频率/码窗口是否跨了NCO换字或slew；
- 同步失效门是否只看自身phase ratio而没看局部物理完整性。

对于B1C，应同时查看`b1c_wide_*`、coarse、slew、center、fine、pilot和lock事件链。

## 15.11 情况F：outage恢复时间不合理

先查测试时间轴：

- outage起止是否在20 ms网格；
- plateau区间是半开区间$[t_0,t_1)$还是闭区间；
- pilot offset是否加入StarGen总时长；
- analyzer是否把绝对流时间和相对handoff时间混淆；
- 恢复是否从第一个完整新窗口计起。

许多“恢复慢20 ms”其实是场景插值边沿没有严格对齐，而不是环路算法差一拍。

## 15.12 常用只读命令

在源码仓库根目录：

```bash
git status --short --branch
rg -n "目标字段或函数" include src tests tools
sed -n '起始行,结束行p' 路径
ctest --test-dir build-release -R test_name --output-on-failure -j 1
```

查CSV时优先用带列名的Python或专用分析器，不要硬编码列号。长真实IQ必须保存scenario、track、pdi、events和summary SHA。

## 15.13 不能用的调试捷径

- 用场景真值在生产代码里选峰；
- 为单个seed加条件分支；
- 把负修改功率取绝对值；
- 放宽5/10 Hz或0.2 chip门掩盖发散；
- 用显示C/N0或FLL残差冒充物理C/N0；
- 看到final state不同就改状态机；
- 只看`sync`或最终15 s，不找第一错误历元；
- 混用不同StarTrack/StarGen SHA的结果组成一份资格。

## 15.14 本章小结

调试从层级和时间轴开始：PDI是否真实、观察是否正确、环路是否使用、命令是否确认、FSM是否按证据提交。找第一错误历元比分析最终均值更有效。频率、码、同步和状态字段都有不同物理语义，不能互相替代。
